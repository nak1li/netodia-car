# 车机音乐 App 架构设计

目标设备：**Allwinner T3 车机 / Android 4.4.2 (API 19) / 32 位 ARM / 4G CGNAT**

参考项目：Netodia、netease-music-gpui、Siren（均为桌面 Rust 项目）→ 技术栈不可直接移植，
**取其设计意图**（见下），在 Android 4.4 上以原生 Java 重写。

---

## 1. 为什么不能直接用参考项目

| 项目 | 技术栈 | 最低平台 | 对 T3 (API 19) |
|---|---|---|---|
| Netodia | Rust + egui | Windows/Linux 桌面 | 不可移植 |
| netease-music-gpui | Rust + GPUI | 桌面 | 不可移植 |
| Siren | Rust + Tauri | 桌面 | 不可移植 |

三个都是**桌面**客户端。T3 是 API 19 的嵌入式 Android，任何 Rust GUI 栈（egui/GPUI/Tauri）
都需要 Android 7+（Tauri Android 需 API 24+，GPUI 需 Android 10+）。

**结论：车机端重写为原生 Android Java（API 19），服务端复用参考项目的网易云 API 逻辑。**

---

## 2. 总体架构：服务端 + 车机瘦客户端

```
┌──────────────────┐   出向 HTTPS/HTTP    ┌─────────────────────────┐
│  车机 T3         │ ───────────────────> │  自建服务器 <你的服务器IP> │
│  Android 4.4.2   │ <─────────────────── │  ncm-server             │
│  Netodia-Car.apk│   音频流(CDN直连)     │  ├ 网易云 API 代理      │
│                  │                       │  ├ 服务端音频缓存      │
│  本地缓存 L1     │                       │  └ 歌单/搜索/歌词      │
└──────────────────┘                       └─────────────────────────┘
```

### 为什么必须有服务端

1. **车机在 4G CGNAT 后面**，只能出向连接，无法被家里反向连入。
   服务端需要有公网入口（端口映射或内网穿透），车机主动连过去即可。
2. **网易云风控**：直接由车机请求 `music.163.com`，匿名请求会被限流/拒绝
   （实测 `search/pc` 返回 `-462` 验证拦截）。服务端持有登录 cookie，
   请求从固定 IP 发出，风控友好得多。
3. **升级成本**：车机不可物理到达（见 skill `legacy-android-provisioning`）。
   任何需要改车机端代码的修复都要人跑过去。**因此协议兼容层必须坐在服务端**，
   车机端只保留"播放 + 缓存 + UI"三件事。
4. **账号凭据**：网易云 cookie 放服务端，车机 APK 里不嵌任何账号信息。

### 音频走 CDN 直连还是经服务端中转？

**决定：服务端中转（proxy），但缓存命中时零上游流量。**

- 直连 CDN：车机直连 `m*.music.126.net`，快，但车机每次都要过公网，车机流量费高，
  且无法在服务端统一缓存。
- 服务端中转：车机只跟自建服务端通信（同一 WiFi 下零公网流量），服务端可做**二级缓存**，
  命中即本地发盘，不产生上游流量和风控请求。

代价：音频流过家里服务器。实测 320k MP3 单曲 4.5MB，局域网吞吐完全够。

## 3. 缓存策略（核心）

需求是"设计好足够优秀的缓存策略"。分层 + 多级淘汰 + 预取。

### 3.1 三层缓存

```
L0  内存缓冲   车机进程内，播放中的当前流
L1  车机本地磁盘  /data/data/<pkg>/files/cache/    ← 车机侧
L2  服务端磁盘   ~/.ncm-cache/audio/<songid>.<ext> ← 服务端侧
```

### 3.2 L2 服务端缓存（主力）

| 项 | 设计 |
|---|---|
| 键 | `<songId>.<quality>.<ext>`，如 `3440441479.exhigh.mp3` |
| 命中 | 直接从本地文件发盘，**零上游请求** |
| 未命中 | 先问网易云拿 URL，再回源下载，落盘后发给车机（边下边发） |
| 上限 | 默认 20 GB，LRU 淘汰 |
| 淘汰 | 按 `atime` 升序删最旧的，直到低于上限；保留正在被请求的 |
| 过期 | 音频文件永久有效（与网易云 URL 时效无关）；**只有元数据/URL 缓存有 TTL** |
| 并发去重 | 同 songId 的并发请求共用一个下载 Promise，不重复打上游 |

**关键点：网易云 CDN URL 带时效戳**（实测 URL 路径含 `20261029004242`），几十分钟后失效。
所以 **缓存的必须是"音频字节"而不是"URL"** —— 缓存 URL 会周期性 404，缓存字节则永久有效。
这是整个缓存设计里最容易踩的坑。

### 3.3 L1 车机本地缓存

| 项 | 设计 |
|---|---|
| 目录 | 应用私有目录 `files/cache/`，无需存储权限，卸载即清 |
| 键 | 同 L2，`<songId>.<quality>.<ext>` |
| 上限 | 默认 512 MB（车机存储小），可在设置里调 |
| 淘汰 | LRU + **手动锁定**（用户点"收藏下载"的歌曲永不淘汰） |
| 写入 | 流式下载边写边播，`.part` 临时文件 → 完成后 rename 原子提交 |
| 校验 | 落盘前校验 `Content-Length` 与实际字节数一致，不一致丢弃 |
| 断点续传 | 下载中断时保留 `.part`，下次用 HTTP `Range` 续传（实测 CDN 支持 206） |

### 3.4 预取策略（体验关键）

| 场景 | 动作 |
|---|---|
| 开始播放第 N 首 | 立即在后台预取第 N+1 首的 L1 缓存 |
| 歌单/队列剩余 ≤ 2 首 | 预取剩余全部 |
| 缓存空间不足 | 停止预取，优先保正在播放的 |
| 网络类型 | 移动网络（4G）下**默认不预取**，避免烧流量；WiFi 下自动开预取 |

第 N+1 首的预取走 L2：车机向服务端请求预取，服务端提前把文件拉到 L2，
车机再拉一次。这样即使车机第一次播放这首都极快（服务端已缓存）。

### 3.5 缓存与音质的关系

实测（匿名 cookie）：

| level | 码率 | 结果 |
|---|---|---|
| standard | 128k | mp3, 1.8MB |
| exhigh | 320k | mp3, 4.5MB |
| lossless/hires | — | **降级为 320k mp3**（需 VIP 账号） |

所以音质分档必须**按实际拿到的码率**回填，不能假装给了 FLAC。
登录后（服务端持有 VIP cookie）才能真正拿到 lossless。
缓存键包含 quality，所以音质变了缓存自然失效重建，不会串味。

## 4. 车机端技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Java（source/target 8） | API 19 兼容性最好，构建链已跑通（aapt2→javac→d8） |
| 播放 | `android.media.MediaPlayer` | **不引 ExoPlayer/Media3**：Media3 最低 API 21，ExoPlayer 2.x 带 so 会让 APK 涨 2-3MB。车机只要能播 mp3/aac，够用 |
| UI | 原生 `View` + XML | 不用 Compose（要 Kotlin 编译器，体积/构建复杂度上去了） |
| 网络 | `HttpURLConnection` | 4.4.2 上够用；OkHttp 会加 ~800KB |
| 存储 | `File` + `SharedPreferences` | 不引 Room/SQLite ORM |
| JSON | `org.json` | Android 自带，不用 Gson/Jackson |
| 构建 | 免 gradle：`aapt2 → javac → d8 → zipalign → apksigner` | 工具链已在 `~/android-build`，见 skill reference |

**目标 APK 体积 < 400KB**（不含图标资源）。

## 5. 车机端功能范围

从参考项目提炼的设计意图（而非照搬功能）：

| 参考项目设计点 | 在车机版的落地 |
|---|---|
| Siren 的"极简播放页" | 单页播放界面：大封面 + 歌名/歌手 + 进度条 + 大按钮。**开车场景下信息密度要低** |
| Netodia/gpui 的歌单浏览 | 侧栏歌单列表 → 歌曲列表 → 播放页，三层导航 |
| Siren 的离线/下载管理 | 下载管理页：查看已缓存曲目、手动清理、锁定收藏 |
| gpui 的歌词滚动 | 播放页可切换歌词视图，逐行高亮 |

**车机专属适配**（参考项目都没有的）：

- **大字号大按钮**：1024×600 类车机屏，触摸操作，按钮 ≥ 64dp
- **深色主题**：夜间驾驶不刺眼
- **防误触**：播放/暂停做得大且区分度极高
- **开机自启 + 后台保活**：`BroadcastReceiver` 监听 `BOOT_COMPLETED`
- **车辆模式**：连接 WiFi 时自动进入，息屏不中断播放
- **离线可用**：无网络时只显示已缓存内容

## 6. 服务端接口

车机只认这组简洁接口（**不要把网易云的原始接口直接暴露给车机**，
否则网易云一改协议就得重装 APK）：

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/search?q=&type=` | GET | 搜索（type: 1 歌曲 / 1000 歌单 / 10 专辑） |
| `/api/playlist/detail?id=` | GET | 歌单详情 + 曲目 |
| `/api/playlist/recommend` | GET | 推荐歌单 |
| `/api/toplist` | GET | 榜单 |
| `/api/song/url?id=&quality=` | GET | 取播放地址（服务端去网易云拿） |
| `/api/stream?id=&quality=` | GET | **音频流**（服务端代理 + 缓存） |
| `/api/lyric?id=` | GET | 歌词 |
| `/api/cache/status` | GET | 缓存占用统计 |

## 10. 参考项目调研结论（2026-10-29）

三个参考项目全部是**桌面 Rust 栈**，硬件与 API 双重不可达：

| 项目 | 栈 | 最低 Android | 到 T3 (API 19) 的硬墙 |
|---|---|---|---|
| Netodia | Rust + egui | 桌面 | 无 Android 平台层 |
| netease-music-gpui | GPUI 0.3.8 + wgpu | **API 26 / arm64** | ① Mali-400 只有 GL ES 2.0、无 Vulkan，GPUI 渲染器起不来 ② API 26 vs 19 ③ NDK r26 起最低 API 21 ④ armv7 路径官方标注未测试 |
| Siren | GPUI + libmpv | **API 21+**（实际 26） | ① 编译期 `compile_error!` 拒绝非桌面平台 ② libmpv Android 构建基线 API 21 ③ `directories` 在 Android 返回 None → 四层缓存全废 |

**结论：不可能移植，只能借设计。** 三处已采纳：

### 10.1 缓存键：不存 URL，存字节（已验证过的判断）
gpui 项目的做法印证了这一点：网易云的播放地址带签名会过期，用 URL 做键会导致每次重新签名都 miss。

### 10.2 歌词负缓存（已实现）
来自 Siren：歌词「查不到」是常态（纯音乐、冷门曲），不缓存空结果会导致每次播放都重打必然失败的请求。实现：空结果也落盘，TTL 12h（正常结果 7d）。

### 10.3 容量计数增量记账（已实现，并抓出 2 个真 bug）
每次下载都 `readdir + stat` 全目录，在几千首缓存时会明显变慢。改为增量记账，超上限才扫盘。

**实测抓出的两个 bug（都是"看起来能跑"的类型）：**
1. `evict()` 把 `keepBytes` 当成额外余量减掉，导致判定「还没超上限」→ **缓存永不淘汰**，会无界涨到 20GB 上限都拦不住
2. 加了增量记账后，`evict()` 删了文件却没同步计数 → 计数虚高 → **后续也永不淘汰**

两条都是静默失败：日志正常、接口 200、只有缓存目录在悄悄变大。

### 10.4 现成 App 的可行性（实测 APK 清单，非抄 README）

能装到 API 19 的：

| App | 体积 | minSdk | 有无网易云 |
|---|---|---|---|
| Vinyl Music Player | 7.8 MB | 19 | 无（纯本地） |
| K19 Player | 9.8 MB | 19 | 无 |
| LittleMusicPlayer | 0.02 MB | 1 | 无 |
| Listen1 | 23 MB | 16 | 有，但无下载/缓存 |

装不上的（双重不可装）：**网易云官方车机版 3.5.12 · 35.8 MB · minSdk 21 · 仅 arm64-v8a**、MusicFree（24）、Salt Player（24）。

**结论：自研是唯一能同时满足「网易云 + 离线缓存 + API 19」的路。** 自研 APK 69 KB，比最小的现成同类（Vinyl 7.8 MB）小两个数量级。

### 10.5 Android 4.4 的编码限制
不支持 Opus / APE / WavPack。服务端统一输出 MP3（当前实测 320k）或 FLAC，**不要指望车上解这些格式**。
